The candidate method is a final source check of proposed curator questions. These observations are not human phone confirmations.

`support-package.zip`, `support-editorial-review.json`, and `distillation.json` exercise the real evidence import and method-distillation path. The resulting lesson is stored as JSON and immutable database records. No resource-specific condition is added to Scout code.

Six fresh Denver-area Employment leads are given to two independent Astra sessions. They receive the same playbook, neutral instructions and budgets, with only the proposed addition differing. The previous lesson is not included in either arm. The coordinator keeps the rubric, support examples and opposing results out of both contexts.

Canonical packets contain routing metadata. The exact archived delivery packets omit only `arm`, `contextId` and `trialId`, so respondents do not see baseline/candidate labels. Their assignment hashes still reference the canonical packet; the archived delivery and prompt hashes establish what was actually transmitted.

`rubric.json` was sealed before dispatch. It requires at least two fewer avoidable question issues across two cases, with no newly suppressed consequential question or material factual/detail/selection error, before calling the result promising. A source newly found by one arm is a separate retrieval improvement, not proof the other arm ignored a source it reviewed. The confirmation rule is predeclared; there is no repeat-until-positive loop.
